Every library · The source

What it's for

Numbers on the graphics card, worked on there: NVIDIA's, through CUDA's driver (DESIGN §158). Lists of numbers go up to the card, as 32-bit floats, as graphics cards keep them, are added, multiplied, matrix-multiplied and summed there, thousands at a time, and come back as lists. The card's code is written here in PTX, which the driver makes the card's own as it loads, so nothing but the driver is needed: no CUDA toolkit.

use "gpu.folio" as gpu
if gpu's available()
    say gpu's device()                          # its name, memory, capability and processors
    set a to gpu's upload(list of 1, 2, 3)      # on the card
    set b to gpu's upload(list of 10, 20, 30)
    say gpu's download(gpu's plus(a, b))        # [11, 22, 33]
    say gpu's sum(a)                            # 6
end

For learn.folio, which trains networks on the card: transpose, add_rows (a row added to each row), column_sums, softmax_rows, cross_entropy (each row's softmax against its label, its loss and gradient at once), argmax_rows, relu_gradient, add_scaled (in place) and adam_step; matmul_turned (a side turned over, into a gradient), column_sums_into and adam_many (every parameter in a launch, with AdamW's decay and clipping if wanted), sum_of_squares (of many at once) and dropout_mask. Memory free gives back is kept for the next numbers of as many, as a training loop makes the same sizes over and over; give_back_memory() hands it to the driver. For transformers: gather_rows and scatter_add_rows (an embedding and its gradient), gelu and gelu_gradient, layer_norm and layer_norm_gradient, and attention and attention_gradient, with a causal mask.

A program that uses it is run or built with --allow-libraries. On a computer with no NVIDIA card, or no driver, available() is no and the rest is a fail with that says so. Numbers on the card are floats: about 7 digits, not Folio's 15, as machine learning wants them.

Kernels of your own (DESIGN §176), written in PTX as gpu.folio's are, and run on as many threads as you say:

set ptx to read "saxpy.ptx"                     # .version, .target, and .entry saxpy(...) { ... }
set saxpy to gpu's kernel(ptx, "saxpy")         # its inputs' types, from its .entry line
set x to gpu's upload(list of 1, 2, 3)
set y to gpu's upload(list of 10, 20, 30)
gpu's launch(saxpy, 1, 256, list of y, x, 2.5, 3)   # 1 block of 256 threads: y = 2.5 x + y, for 3 numbers
say gpu's download(y)                           # [12.5, 25, 37.5]

kernel(ptx, name) loads a module once, however many of its kernels are asked for, and a mistake in it is a fail with that says what the driver said, with the line. launch(kernel, grid, block, inputs) runs it on a grid of blocks of threads, each a number or a list of 1 to 3 (x, y, z); launch_with(kernel, grid, block, shared, inputs) gives each block shared bytes of the card's fast memory too (.extern .shared). Each input is given as its .param says: numbers or bytes on the card for a 64-bit one (.u64, .b64, .s64: where they are), a number for .f32 or .f64, and a whole number in range for the rest (.u8 to .s64). A launch doesn't wait: the next download, download_bytes or finish() does, and says a mistake the kernel made there (an address outside what it was given, say), after which the card does nothing more for the program, as CUDA has it. For whole numbers, or anything else, on the card: upload_bytes(bytes), room(size) (that many bytes, each 0), and download_bytes(g); memory.folio puts numbers of C's kinds into bytes and takes them out.
